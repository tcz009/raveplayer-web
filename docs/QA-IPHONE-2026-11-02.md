# iPhone/PWA QA — 2026-11-02 (1.6.28 fixes)

Two HIGH issues found during the iPhone/PWA pass. Both are fixed on
`feature/1.6.28-iphone-fixes`; this is the evidence trail.

## HIGH 1 — background jobs were per-gunicorn-worker

**Observed:** the same job id returned 200 on 6/8 polls and 404 on 2/8; the job
list omitted it in 1/12 requests; the topbar chip showed 0% and then vanished;
`jobs.json` writes from one worker could clobber the other's jobs.

**Root cause:** the 1.6.23 job state lived in a process-global dict
(`_DOWNLOAD_JOB_STATE`) and was persisted by read-modify-write of
`downloads/jobs.json`. With `gunicorn -w 2`, create landed in one worker and
polls often hit the other, which had no row.

**Fix (1.6.28):** jobs now live in the shared auth SQLite database
(`RAVEWEB_AUTH_DB`, default `$RAVEWEB_DATA/auth.sqlite3`) in the
`download_jobs` table (WAL). Transitions are transactional:

- `create` inserts `queued`;
- a per-process scheduler claims the oldest queued row with
  `BEGIN IMMEDIATE` only when the global `downloading` count is below
  `RAVEWEB_DOWNLOAD_JOBS` (1–2), setting `worker_pid`/heartbeat;
- progress/heartbeat, complete, fail and cancel are atomic SQL updates;
  complete refuses a cancelled row and removes an unindexed file;
- `recover_orphans` fails a `downloading` row whose worker pid no longer exists;
- the old `jobs.json` is migrated once and removed;
- cancel/list/detail read the shared table, so either worker returns the same
  state.

**Evidence:** `test/test_download_jobs.py::test_shared_store_across_processes_no_clobber`
spawns two OS processes creating jobs against one DB, then verifies both rows
survive (no clobber), one can be claimed/completed and the other cancelled, with
the final states visible from the parent. Existing lifecycle/cancel/concurrency/
recovery tests also pass. UI polling (`/api/downloads/jobs` every ~1.6s) shows
queued/downloading/completed consistently from either worker.

**Residual:** job metadata is not pruned yet; scheduler polls every 0.4s only
while a jobs endpoint has been hit in that process. A process that dies after
inserting a queued row leaves it claimable by another worker (fine), not
orphaned UI state.

## HIGH 2 — mobile search overflowed and covered the submit button

**Observed at 390px viewport:** input measured ~234px inside a 65px field;
`document.scrollWidth` 406px; the 44px submit button was covered
(`document.elementFromPoint` returned the input).

**Root cause:** the `.search` row was `width:100%` but its child input carried
`width:auto`/intrinsic sizing at the ≤620 breakpoint; flex min-content width
pushed the row past the viewport and the button under the input.

**Fix (1.6.28):** mobile search rules in `static/app.css`: `.search` and
`.search-field` get `min-width:0`/`max-width:100%`; the input is
`width:100%; min-width:0; box-sizing:border-box`; submit is a fixed
`flex:0 0 44px` 44×44 target with `z-index:2`; topbar clips horizontal overflow.
Desktop layout unchanged.

**Evidence:** Playwright
`test_e2e/test_smoke.py::test_mobile_search_field_fits_and_submit_is_tappable`
at 390×844 asserts document width ≤ viewport, input inside field, input width
≥120px, submit ≥44×44, submit right within search, and
`elementFromPoint(button centre).closest('button')` is the submit button.

## Also in 1.6.28

- **`GET /manifest.json` alias** now serves the same manifest JSON as
  `/manifest.webmanifest` (both public; tests assert equality).
- **Service worker cache** bumped from `raveplayer-shell-v1.6.19` to
  `raveplayer-shell-v1.6.28`; registration remains on the root-scoped worker.
- **Cookie `Secure`** remains HTTPS-only (per-request
  `_HttpsAwareSessionInterface` + `X-Forwarded-Proto`); plain-HTTP LAN login
  still works and no Secure cookie is emitted there. Documented in
  `docs/AUTH.md`.

## Recommended owner follow-up

- After deploy, hard-reload once so the new service worker cache activates;
  old 1.6.19 caches are deleted by the activate handler.
- Old sessions/jobs from pre-1.6.28 are handled by orphan recovery/migration;
  sign in once after deploy if your cookie predates the 1.6.23 session store.
